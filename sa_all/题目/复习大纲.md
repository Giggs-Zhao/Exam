# 上篇：基础知识（★★★）

## 1. 绪论（★★☆）

### 1.1 系统架构概述

- **系统架构定义**：系统整体高层结构，由构件、连接件、约束、原则及演化机制组成；目标是指导系统设计、实现、部署和演化。
- **架构发展主线**：模块化 → 面向对象 → 构件化 → 面向服务 → 云计算/云原生。
- **四类架构模型**：结构模型（构件、连接件、约束）、框架模型（面向问题域的整体框架）、动态模型（运行、重配置、演化）、过程模型（构造步骤和过程脚本）。
- **模块化原则**：高内聚、低耦合、适度粒度、接口简洁、信息隐藏、复用已有模块。
- **组件化与模块化区别**：模块主要是逻辑切分；组件具有物理隔离、自包容、可组装、可插拔和独立部署能力。

### 1.2 架构师职责与能力

- 将业务目标、约束和质量属性转换成可实施的架构决策。
- 管理需求、风险、技术债、架构文档、评审和演化。
- 具备业务理解、技术广度、建模表达、权衡取舍、沟通协作和项目治理能力。

### 1.3 高频题联动

- 选择题：基本概念、架构描述语言、软件架构基础、架构复用。
- 论文题：软件架构建模、非功能需求与架构设计、架构演化。
- 案例题：构件化与插件架构、软件架构风格与模式。

## 2. 计算机系统基础知识（★★☆）

### 2.1 硬件与处理器

- 计算机组成：运算器、控制器、存储器、输入输出和总线。
- CISC 与 RISC：指令数量、寻址方式、控制方式、流水线适配、编译器依赖。
- 专用处理器：GPU 适合大规模并行，DSP 适合实时数字信号处理，FPGA 适合可编程硬件逻辑。
- 存储层次：寄存器 → Cache（SRAM）→ 主存（DRAM）→ 外存；注意速度、容量、成本的权衡。
- 总线和 DMA：总线带宽、传输方式、DMA 对 CPU 占用的影响。

### 2.2 操作系统与文件系统

- 操作系统四特征：并发性、共享性、虚拟性、不确定性。
- 操作系统类型：批处理、分时、实时、网络、分布式、微型机。
- 进程管理：进程/线程、同步互斥、死锁四条件、调度算法、前趋图。
- 内存管理：分页、分段、虚拟存储、页面置换、地址转换。
- 文件系统：连续、链接、索引结构；位示图、索引节点、直接/一级间接/二级间接地址计算。
- 计算重点：块数、位号/字号、文件最大长度、页面命中和缺页次数。

### 2.3 中间件与构件

- 中间件位于操作系统和应用之间，提供通信、事务、消息、数据访问、容器和服务治理能力。
- 构件标准：CORBA、J2EE 等；理解容器、接口、配置、打包和运行管理。

### 2.4 嵌入式基础

- 嵌入式系统：面向特定应用，资源受限，软硬件一体，代码固化，实时性、安全性和可靠性要求高。
- 软件层次：硬件层、硬件抽象层/BSP、操作系统层、中间件层、应用层。
- 六个关键词：可裁剪、可配置、强实时、安全、可靠、高确定性。
- 题目联动：`选择题_计算机组成原理_完整题目答案解析.md`、`选择题_操作系统_完整题目答案解析.md`、`案例题_嵌入式系统架构设计_完整题目答案解析.md`。

## 3. 信息系统基础知识（★☆☆）

### 3.1 信息系统与生命周期

- 信息系统：以数据为核心，通过人员、流程、技术和组织规则支持业务目标。
- 生命周期：规划、分析、设计、实施、运行维护、退役/演化。
- 建设原则：整体规划、标准先行、数据共享、安全可控、适度超前、持续演化。
- 开发方法：结构化、面向对象、原型、敏捷、迭代、基于构件和模型驱动。

### 3.2 典型信息系统

- TPS：处理日常事务，强调准确、稳定和高吞吐。
- MIS：面向管理信息汇总、查询和报表。
- DSS：为半结构化决策提供模型、数据和分析。
- ES：知识库、推理机、解释机制和人机接口。
- OAS：办公流程、协作和信息共享。
- ERP：财务、采购、生产、库存、人力等资源的集成管理。
- 电子政务、企业信息化、电子商务：关注业务协同、数据共享、流程再造和安全合规。

## 4. 信息安全技术基础知识（★★★）

### 4.1 安全目标与体系

- CIA：保密性、完整性、可用性；补充不可抵赖性、可审计性和真实性。
- 安全体系：技术体系、组织机构体系、管理体系。
- 风险管理流程：资产识别 → 威胁/脆弱性分析 → 风险评估 → 风险处置 → 监控复审。
- 等级保护：按系统重要程度和受破坏后的影响进行分级保护。

### 4.2 密码、认证与访问控制

- 对称加密：速度快，适合大数据量；重点理解密钥分配。
- 非对称加密：公钥/私钥，适合身份认证、密钥交换和数字签名。
- 混合加密：公钥加密会话密钥，对称密钥加密业务数据。
- 数字签名：私钥签名、公钥验证，提供完整性、真实性和不可抵赖性。
- PKI：CA、证书、注册机构、证书吊销和密钥生命周期。
- 访问控制：自主、强制、基于角色、基于属性；最小权限、职责分离、默认拒绝。

### 4.3 攻击与防护

- 拒绝服务、欺骗、端口扫描、漏洞利用、重放、中间人、注入和越权。
- 防护组合：身份认证、授权、加密、输入校验、网络隔离、日志审计、备份恢复、入侵检测与应急响应。
- 数据库安全：透明加密与 API 加密的适用场景；完整性约束；最小权限和审计。
- 题目联动：`选择题_信息安全_完整题目答案解析.md`、`案例题_系统安全_完整题目答案解析.md`、`论文题_网络安全_完整题目答案解析.md`。

## 5. 软件工程基础知识（★★★）

### 5.1 软件过程模型

- 瀑布、原型、增量、螺旋、迭代、敏捷；掌握适用条件、优缺点和风险。
- RUP 四阶段：初始、细化、构造、移交；核心工作流贯穿迭代。
- CMM/CMMI：过程成熟度、能力域、持续改进。

### 5.2 需求工程

- 需求层次：业务需求、用户需求、功能需求、非功能需求。
- 活动：获取、分析、规格化、验证、管理、追踪和变更控制。
- 非功能需求必须可度量，建议写成质量属性场景：刺激源、刺激、环境、制品、响应、响应度量。
- 需求变更：提出、影响分析、审批、实现、验证、基线更新。

### 5.3 分析、设计、构件与测试

- 结构化方法：数据流图、数据字典、加工说明、结构图。
- 面向对象方法：类、对象、封装、继承、多态、关联、聚合、组合。
- 构件化开发：构件获取、适配、组装、配置、验证和演化。
- AOP：把横切关注点从核心业务中分离。
- 测试层次：单元、集成、系统、验收；静态测试和动态测试；白盒、黑盒、灰盒。
- 覆盖标准：语句、判定、条件、条件组合、路径；区分回归测试、确认测试和性能测试。
- 质量保证：评审、审计、度量、缺陷管理、配置管理和持续改进。

### 5.4 项目管理

- 范围、进度、成本、质量、资源、沟通、风险、采购和干系人管理。
- 关键工具：WBS、网络图、关键路径、挣值、风险登记册、配置基线、燃尽图。
- Scrum：产品待办、迭代待办、增量、产品负责人、Scrum Master、开发团队；注意敏捷不是无计划。

## 6. 数据库设计基础知识（★★★）

### 6.1 数据模型与关系数据库

- 三级模式：外模式、概念模式、内模式；两级映像实现数据独立性。
- 关系模型：关系、元组、属性、域、候选键、主键、外键。
- 关系代数：选择、投影、连接、并、交、差、笛卡尔积。
- 函数依赖、候选键和范式：1NF、2NF、3NF、BCNF；以消除冗余和更新异常为目标。

### 6.2 数据库设计过程

- 需求分析 → 概念结构设计（ER）→ 逻辑结构设计 → 物理设计 → 实施 → 运行维护。
- ER 转关系：实体表、联系表、主外键、1:1、1:N、M:N。
- 反规范化：在可接受一致性代价下换取查询性能；必须配合约束、缓存和同步策略。

### 6.3 事务、并发与分布式数据库

- ACID；并发异常：丢失更新、脏读、不可重复读、幻读。
- 隔离级别：读未提交、读已提交、可重复读、串行化。
- 锁、MVCC、日志、恢复、检查点、两阶段提交和最终一致性。
- NoSQL：键值、文档、列族、图数据库；理解 CAP、BASE、分片和副本。
- 数据访问：JDBC/接口、嵌入 SQL、ODBC、ORM；关注连接池、事务边界和 N+1 查询。

## 7. 系统架构设计基础知识（★★★）

### 7.1 软件架构概念与生命周期

- 架构是决策集合，不只是静态图；决策必须关联需求、约束、质量属性、风险和验证方式。
- 基于架构的软件开发：需求 → 架构设计 → 文档化 → 评审 → 实现 → 演化；每一步都保留可追踪关系。
- 架构描述语言：构件、连接件、配置、约束、语义和视图；能表达结构、行为和质量属性。

### 7.2 架构风格

- 数据流：批处理、管道-过滤器；适合逐步转换和流式处理。
- 调用/返回：主程序-子程序、面向对象、层次、客户端/服务器。
- 数据中心：仓库、黑板；适合共享数据和多知识源协作。
- 虚拟机：解释器、规则系统；适合跨平台和动态规则。
- 独立构件：事件驱动、发布订阅、消息总线；适合解耦和异步扩展。
- 常考风格：MVC、分层、微内核、插件、SOA、微服务、事件驱动、管道过滤器、黑板、仓库。
- 每种风格都要会写：结构、优点、缺点、适用场景、质量属性影响和改进措施。

### 7.3 架构复用与 DSSA

- 复用对象：需求、设计、构件、框架、模式、文档和测试资产。
- 复用过程：领域分析 → 资产组织 → 检索匹配 → 适配组装 → 验证反馈。
- DSSA：特定领域参考需求、参考架构、领域构件和变体点；掌握领域工程与应用工程区别。

### 7.4 架构文档与 4+1 视图

- 逻辑视图、开发视图、进程视图、物理视图和场景视图。
- 文档至少描述：背景和目标、约束、利益相关者、架构决策、视图、接口、部署、质量属性、风险、演化和追踪关系。

## 8. 系统质量属性与架构评估（★★★）

### 8.1 质量属性

- 性能、可用性、可靠性、安全性、可修改性、可测试性、可部署性、易用性、互操作性、可扩展性、可移植性。
- 质量属性互相制约：安全可能增加延迟；一致性可能降低可用性；高性能可能增加复杂度。
- 场景六要素：刺激源、刺激、环境、制品、响应、响应度量。度量必须可验证。

### 8.2 评估方法

- 基于场景、基于模拟、基于度量、基于经验和基于模型。
- ATAM：演示架构 → 调查和分析 → 测试/权衡 → 报告；识别敏感点、权衡点和风险。
- 评估输出：质量属性效用树、场景优先级、风险清单、非风险、敏感点、权衡点和改进建议。

### 8.3 案例答题句式

> 先指出目标质量属性，再说明当前架构中的瓶颈，提出可落地的架构措施，最后写出代价、风险和验证指标。

## 9. 软件可靠性基础知识（★★★）

- 可靠性：规定条件、规定时间内完成规定功能的能力；可用性还要考虑维修和恢复。
- 指标：失效率、平均无故障时间 MTBF、平均修复时间 MTTR、可靠度、可用度、故障密度。
- 可靠性模型：失效率模型、定时操作模型、输入域模型、故障植入模型等；注意模型假设。
- 容错设计：冗余、故障检测、隔离、降级、重试、超时、熔断、自动切换、状态恢复。
- 检错技术：断言、校验和、心跳、看门狗、异常检测、故障树 FTA、FMEA。
- 可靠性测试：定义运行剖面、设计用例、注入故障、测量失效和恢复、评估模型。
- 题目联动：`选择题_系统可靠性_完整题目答案解析.md`、`论文题_系统可靠性_完整题目答案解析.md`。

## 10. 软件架构演化和维护（★★☆）

- 演化原因：业务变化、技术替换、规模增长、质量属性目标变化、法规和组织变化。
- 静态演化：版本、部署、结构和接口改变；动态演化：运行时重配置、弹性伸缩和热升级。
- 演化原则：保持核心业务稳定、隔离变化点、兼容接口、可回滚、可观测、渐进迁移。
- 大型网站演化链：单体 → 垂直拆分 → 缓存 → 集群 → 读写分离 → 反向代理/CDN → 分布式文件/数据库 → NoSQL/搜索 → 业务拆分 → 分布式服务。
- 维护管理：架构知识库、变更评审、版本管理、技术债管理、可维护性度量。

# 下篇：架构设计理论与实践（★★★）

## 12. 信息系统架构设计（★★☆）

- 信息系统架构关注业务、数据、应用和技术四个层面，以及治理、安全、标准和组织。
- 常见模型：企业架构分层、业务/应用/数据/技术架构、集成架构、总体架构和部署架构。
- ADM 思路：架构愿景 → 业务架构 → 信息系统架构 → 技术架构 → 机会和解决方案 → 迁移规划 → 实施治理 → 变更管理。
- 设计步骤：业务目标和干系人识别 → 现状评估 → 目标架构 → 差距分析 → 路线图 → 治理和度量。
- 案例重点：价值驱动、Web 服务、企业整合、共享能力、主数据和架构治理。

## 13. 层次式架构设计（★★★）

### 13.1 分层思想

- 表现层：界面、输入校验、会话和展现；常见 MVC、MVVM、UIP。
- 业务层：领域模型、业务规则、工作流、服务编排和事务边界。
- 数据访问层：DAO、工厂、ORM、连接池、缓存、事务和异常转换。
- 数据架构：数据库、文件、XML/JSON、主数据、数据仓库和数据治理。

### 13.2 设计原则

- 单一职责、依赖倒置、接口隔离、低耦合、高内聚、事务边界清晰。
- 防止跨层调用、循环依赖、贫血模型滥用、连接泄漏和 N+1 查询。
- 电子商务和物联网案例要能说明：请求链路、领域服务、数据一致性、缓存、消息和部署。

## 14. 云原生架构（★★★）

### 14.1 内涵

- 面向云环境设计，强调容器化、自动化、弹性、可观测、松耦合和持续交付。
- 原则：服务自治、基础设施自动化、声明式配置、不可变基础设施、弹性伸缩、故障隔离。

### 14.2 主要技术

- 容器、镜像、编排、服务发现、配置中心、API 网关、微服务、Serverless、服务网格。
- CI/CD、蓝绿发布、金丝雀发布、滚动升级、自动回滚。
- 可观测性：日志、指标、链路追踪、告警、SLO/SLI。

### 14.3 反模式与取舍

- 反模式：无边界拆分、分布式单体、共享数据库、同步调用链过长、缺少治理、只容器化不自动化。
- 论文要写清：为什么云化、拆分边界、数据一致性、弹性策略、安全、运维和效果。
- 题目联动：`论文题_云相关架构_完整题目答案解析.md`、案例中的微服务与云原生专题。

## 15. 面向服务架构 SOA（★★☆）

- SOA：以业务服务为基本单元，通过标准契约和协议实现复用、组合与集成。
- 核心角色：服务提供者、服务消费者、服务注册中心；核心要素是契约、自治、无状态、可发现和可组合。
- 协议与规范：UDDI、WSDL、SOAP、REST、BPEL；掌握消息、契约和服务质量。
- 设计模式：服务注册表、企业服务总线、服务组合、微服务化。
- 实施过程：识别集成需求 → 业务流程分析 → 服务边界和粒度 → 标准化 → 治理 → 迁移。
- 易错点：服务粒度过大难复用，过小导致调用和治理成本高；无状态不等于没有数据。
- 题目联动：SOA 与企业应用集成选择题、案例题和 `论文题_企业信息化_完整题目答案解析.md`。

## 16. 嵌入式系统架构设计（★★☆）

- 架构关注硬件约束、实时性、功耗、可靠性、安全性、可裁剪和可移植。
- RTOS：任务、优先级、抢占、时间片、信号量、消息队列、事件、定时器和中断。

- CPS/物联网：感知、网络、控制三层；安全威胁包括节点捕获、数据篡改、窃听、拒绝服务和错误转发。

## 17. 通信系统架构设计（★★☆）

### 17.1 网络基础

- OSI 七层：物理、数据链路、网络、传输、会话、表示、应用；TCP/IP 常按网络接口、网际、传输、应用划分。
- 设备层级：中继器/集线器（物理）、网桥/交换机（链路）、路由器（网络）、防火墙（安全控制）。
- 常用协议：ARP、IP、ICMP、TCP、UDP、DNS、DHCP、HTTP/HTTPS、FTP、SMTP、SNMP、IPSec。

### 17.2 网络设计

- 需求：带宽、时延、吞吐、可靠性、可用性、安全、扩展、运维、成本和绿色性。
- 局域网、广域网、移动通信、存储网络、SDN；掌握双栈、IPv4/IPv6、VLAN、路由和高可用。
- 负载均衡：DNS、反向代理、四层、七层、全局流量；说明健康检查、会话保持和故障转移。
- 网络安全：分区分域、零信任、访问控制、加密、审计和入侵防护。

## 18. 安全架构设计（★★★）

### 18.1 安全模型

- 状态机模型：系统状态和安全状态转换。
- Bell-LaPadula：保密性；不上读、不下写。
- Biba：完整性；不上写、不下读。
- Clark-Wilson：良构事务、完整性约束和职责分离。
- Chinese Wall：按利益冲突动态限制访问。

### 18.2 WPDRRC 与网络安全体系

- WPDRRC：预警（Warning）、保护（Protection）、检测（Detection）、响应（Reaction）、恢复（Recovery）、反击/反制（Counterattack）。
- 网络安全体系：认证、访问控制、机密性、完整性、抗抵赖。
- 数据库安全：权限、视图、完整性、审计、备份、透明加密、脱敏和密钥管理。
- 脆弱性分析：资产—威胁—脆弱性—风险—控制措施；结合 FTA、FMEA、威胁建模和安全测试。

### 18.3 安全案例模板

1. 识别保护对象和安全目标。
2. 分析威胁、攻击面、脆弱性和影响。
3. 设计身份、权限、加密、隔离、审计、检测、响应和恢复。
4. 写出性能、成本、可用性和运维代价。
5. 用测试、审计、演练和度量验证。

## 19. 大数据架构设计（★★★）

### 19.1 架构基础

- 特征：数据量大、速度快、类型多、价值密度低、真实性复杂。
- 典型链路：采集 → 传输 → 存储 → 计算 → 服务/查询 → 可视化与治理。
- 技术角色：消息队列、HDFS/对象存储、HBase、关系数据库、NoSQL、ES、流处理和批处理。

### 19.2 Lambda 与 Kappa

- Lambda：批处理层 + 速度层 + 服务层；兼顾完整性和实时性，但维护两套链路。
- Kappa：以流处理为主，统一实时和历史重放；架构更简洁，但对流平台、回放和数据保留要求更高。
- 选型依据：实时性、历史重算、数据规模、运维复杂度、容错和一致性。

### 19.3 数据治理与论文落地

- 数据分层：热、温、冷；按访问频率、成本和保留周期选择介质。
- 数据湖/湖仓：原始数据保留、统一治理、批流一体、元数据和数据质量。

# 重难点专题（按真题失分风险扩展）

## A. 【★★★ 难点】非功能需求如何落到架构决策

### A.1 从模糊要求变成可验证场景

把“系统要快、要稳定、要安全”改写成六元组：

> **刺激源 + 刺激 + 环境 + 制品 + 响应 + 响应度量**

例：高峰期（环境）用户请求（刺激）到达 API 网关（制品），系统在 2 秒内返回 95% 分位响应（响应和度量），并保持错误率低于 0.1%。

### A.2 质量属性到技术措施

| 目标 | 常见措施 | 代价/风险 |
|---|---|---|
| 性能 | 缓存、异步、批处理、索引、分片、连接池、CDN | 一致性、复杂度、成本上升 |
| 可用性 | 集群、冗余、健康检查、自动切换、降级 | 数据同步、运维复杂 |
| 可靠性 | 超时、重试、幂等、熔断、故障隔离、恢复 | 延迟增加、重复执行风险 |
| 安全性 | 身份、授权、加密、隔离、审计、密钥管理 | 性能和开发成本 |
| 可修改性 | 分层、接口、插件、领域边界、配置化 | 抽象过多、运行开销 |
| 可扩展性 | 无状态、水平扩展、分片、消息队列、弹性伸缩 | 分布式一致性和治理难度 |

### A.3 易错

- 把“可靠性”直接等同于“可用性”；可靠性强调无故障完成功能，可用性还包括维修和恢复。
- 只写技术名词，不写响应指标；案例和论文必须写度量。
- 只写收益，不写代价；架构评估最看重权衡。

## B. 【★★★ 难点】架构风格选择与组合

### B.1 选型逻辑

1. 数据是否按固定步骤变换？是：管道-过滤器/批处理。
2. 是否需要共享中心数据？是：仓库/黑板。
3. 是否需要运行时扩展？是：微内核/插件/独立构件。
4. 是否强调业务服务复用和异构集成？是：SOA/ESB。
5. 是否强调团队自治、独立部署和弹性？是：微服务。
6. 是否强调事件解耦和削峰？是：事件驱动/发布订阅。

### B.2 组合风格的答题写法

大型系统通常不是单一风格：入口使用客户端/服务器或 API 网关，内部按分层组织，业务按微服务拆分，异步场景使用事件驱动，数据使用仓库或湖仓，部署使用容器编排。答题时说明每种风格解决的具体问题。

### B.3 易错

- MVC 是表现层组织方式，不等于完整系统架构。
- 分层架构的层不是物理服务器；逻辑分层与部署分层要区分。
- 微服务不是越细越好；边界应由业务能力、数据所有权和团队自治决定。

## C. 【★★★ 难点】分布式一致性、缓存和并发控制

### C.1 缓存问题四件套

- **穿透**：查询不存在的数据；用布隆过滤器、空值缓存、参数校验。
- **击穿**：热点 Key 失效瞬间大量请求打到数据库；用互斥锁、逻辑过期、热点永不过期。
- **雪崩**：大量 Key 同时失效或缓存集群故障；用随机过期、分批预热、限流、熔断和多级缓存。
- **双写不一致**：缓存和数据库先后写入失败；常用“先更新数据库，再删除缓存”，配合重试、延迟双删、消息最终一致。

### C.2 分布式锁

- 必须具备：互斥、可重入（按需）、超时、自动释放、唯一持有者校验、异常释放和可观测。
- Redis 锁不能只写 `SETNX`；要同时设置过期时间，并用唯一 token 删除自己的锁。
- 数据库锁实现简单但吞吐和故障恢复差；高并发场景要说明瓶颈和死锁风险。

### C.3 分布式事务

- 2PC：强一致倾向，协调者单点、阻塞和性能代价明显。
- TCC：Try/Confirm/Cancel，业务侵入大，但可控性高。
- Saga：长事务拆成本地事务和补偿动作，适合长流程和最终一致。
- 可靠消息：本地事务 + 消息表/事务消息 + 重试 + 幂等消费。
- 答题关键：先定义一致性目标，再选方案；不要见“分布式”就套 2PC。

### C.4 限流、熔断和降级

- 限流：令牌桶适合控制平均速率并允许突发；漏桶适合平滑输出。
- 熔断：关闭、打开、半开三态；失败率或慢调用达到阈值后快速失败。
- 降级：返回缓存、默认值、静态页面或关闭非核心功能；必须保证核心链路。

## D. 【★★★ 难点】数据库设计与高并发

### D.1 范式判断

- 1NF：属性不可再分。
- 2NF：1NF 且非主属性完全依赖候选键，重点看联合主键的部分依赖。
- 3NF：2NF 且不存在非主属性对候选键的传递依赖。
- BCNF：每个决定因素都是候选键，要求比 3NF 更严格。
- 规范化减少冗余和异常；反规范化必须写明读多写少、查询性能、一致性补偿。

### D.2 分库分表判断

- **垂直拆分**：按字段或业务拆，减少单表宽度和耦合。
- **水平拆分**：按用户、时间或区域拆，解决数据量和并发规模。
- 分片键要求：访问高频、分布均匀、稳定、可路由；避免热点分片和跨分片事务。
- 主从复制提升读能力和容灾，不等于解决写入扩展。

### D.3 SQL 与 ORM 易错

- 连接池耗尽、事务边界过大、懒加载引发 N+1、分页深翻页、索引失效、全表扫描。
- 设计索引要结合选择性、最左匹配、回表、覆盖索引和写入代价。
- ORM 解决对象关系映射，不会自动解决事务、一致性和性能问题。

## E. 【★★★ 难点】可靠性与故障处理

### E.1 指标和公式

- 可用度近似：`A = MTBF / (MTBF + MTTR)`。
- 串联系统：任一部件失效都会影响系统，可靠度通常为各部件可靠度乘积。
- 并联系统：有冗余时只要一个部件工作即可；需明确独立性和切换假设。
- 失效率、MTBF、MTTR必须结合运行时间、故障数和修复时间解释，不能只背名称。

### E.2 故障处理闭环

检测（心跳、探针、日志、指标）→ 隔离（熔断、摘除、分区）→ 切换（副本、主备、路由）→ 恢复（重试、重放、回滚）→ 复盘（根因、改进、演练）。

### E.3 FMEA 与 FTA

- FMEA：自底向上，逐个分析部件的失效模式、原因、影响和控制。
- FTA：自顶向下，从顶事件用逻辑门分解基本事件。
- 易错：两者方向相反；都不是单纯的测试用例表。

## F. 【★★★ 难点】安全架构与密码应用

### F.1 加密选型

- 大文件：对称加密；密钥交换或保护：非对称加密；身份和不可抵赖：数字签名；实际系统通常使用混合加密。
- 保密性用加密；完整性用哈希/MAC/签名；不可抵赖依赖签名、证书和审计证据。
- 透明加密降低应用改造和管理负担；API 加密灵活，但应用承担密钥和错误处理。

### F.2 访问控制模型

- DAC：资源所有者授权，灵活但容易扩散。
- MAC：按安全级别和规则强制控制，适合高安全场景。
- RBAC：按角色授权，适合组织管理。
- ABAC：按主体、客体、环境属性动态决策，灵活但策略复杂。

### F.3 安全案例结构

资产和目标 → 威胁与脆弱性 → 身份认证 → 授权和最小权限 → 传输/存储保护 → 审计监测 → 响应恢复 → 合规验证。每层写一个具体措施和一个验证方法。

## G. 【★★★ 难点】云原生、微服务与服务治理

### G.1 微服务拆分依据

- 业务能力、领域边界、数据所有权、团队边界、变更频率和伸缩特征。
- 拆分后必须补齐：服务发现、配置、网关、限流、熔断、重试、幂等、链路追踪、日志、指标和告警。

### G.2 数据和调用治理

- 避免共享数据库；每个服务拥有数据边界，通过 API、事件或数据同步交互。
- 同步调用链要设置超时和预算；跨服务重试必须考虑幂等和重试风暴。
- 读模型、CQRS、事件溯源适合复杂查询和审计，但增加一致性和运维成本。

### G.3 发布与运维

- 蓝绿：两套环境快速切换；金丝雀：小流量验证；滚动：逐步替换实例。
- 需要配套自动回滚、数据库兼容、配置版本、SLO、容量基线和故障演练。

## H. 【★★☆ 难点】实时嵌入式与通信网络

### H.1 实时系统

- 硬实时：错过截止期可能导致灾难；软实时：偶尔超时但总体可接受。
- 关注最坏执行时间、任务优先级、抢占、优先级反转、抖动、周期和截止期。
- 优先级反转可用优先级继承或优先级天花板缓解。

### H.2 网络设计

- 时延 = 发送时延 + 传播时延 + 处理时延 + 排队时延。
- DNS 负载均衡简单但受缓存影响；反向代理能做健康检查和七层路由；四层负载更高效，七层更灵活。
- IPv4/IPv6 双栈要考虑地址规划、DNS、路由、防火墙、运维和迁移顺序。

## I. 【★★★ 难点】案例和论文得分点

### I.1 案例题答题卡

- 第一行给结论，避免铺垫过长。
- 第二行引用题干约束：并发、数据量、实时性、安全级别、可用性目标。
- 第三行给架构措施：组件、流程、数据、部署、治理。
- 最后写权衡：收益、代价、风险和验证指标。

### I.2 论文关键决策表

|---|---|
| 架构设计 | 目标、约束、风格、分层、部署、接口、质量属性 |
| 架构评估 | 场景、效用树、敏感点、权衡点、风险、改进 |
| 可靠性 | 冗余、检测、隔离、切换、恢复、演练、指标 |

### I.3 论文易失分

- 项目背景虚构过度，导致后文没有真实约束。
- 只罗列技术名词，没有说明为什么选、怎么落地、效果如何。
- 把“系统采用微服务”当成架构设计，缺少服务边界、数据和治理。
- 效果没有指标；至少给出响应、吞吐、可用性、故障恢复、成本或交付周期中的两类指标。

## J. 【★★★】选择题高频易错清单

- 递归查询与迭代查询方向相反。
- TCP 可靠不代表低延迟；UDP 不可靠不代表不能用于实时系统。
- 主从复制不是分片；缓存不是权威数据源。
- 数字签名不是加密；私钥签名、公钥验证。
- Bell-LaPadula 重点保密，Biba 重点完整性。
- 可靠性不是可用性；错误、缺陷、故障、失效是不同层次。
- 语句覆盖达到 100% 不代表判定、条件和路径覆盖达到 100%。
- 2PC 的参与者都提交不等于没有协调者阻塞问题。
- 微服务拆分后仍共享一个数据库，可能形成分布式单体。
- Lambda 的速度层不是简单的消息队列，Kappa 也不是“不要历史数据”。
# 高频对比与必背清单（★★★）

| 对比 | 记忆重点 |
|---|---|
| 模块化 vs 组件化 | 逻辑切分 vs 物理隔离、可插拔、可独立部署 |
| SOA vs 微服务 | 企业服务复用与集成 vs 细粒度自治、独立部署和快速交付 |
| 分层 vs 微内核 | 固定层次调用 vs 核心系统 + 插件扩展 |
| 同步 vs 异步 | 即时响应、链路耦合 vs 解耦、削峰、最终一致性 |
| CAP 三者 | 分区容错通常必须；一致性和可用性按场景取舍 |
| ACID vs BASE | 强一致事务 vs 基本可用、软状态、最终一致 |
| 主从复制 vs 分片 | 复制提升读可用性；分片扩大数据和写入能力 |
| 缓存旁路 vs 写穿/写回 | 读路径和一致性策略不同；重点防双写不一致、穿透、击穿、雪崩 |
| 对称 vs 非对称加密 | 性能与大数据量 vs 密钥交换、认证和签名 |
| 可靠性 vs 可用性 | 无故障完成规定功能 vs 可访问并可恢复 |
| 失效、错误、缺陷、故障 | 原因和状态链要分清 |
| Lambda vs Kappa | 双链路批流融合 vs 统一流处理与重放 |
| 黑盒 vs 白盒测试 | 外部行为 vs 内部结构和覆盖 |
| 3NF vs 反规范化 | 减少冗余和异常 vs 以可控冗余换性能 |
| 递归查询 vs 迭代查询 | 服务器继续代查 vs 返回下一步地址 |
